## 1. 무엇이 틀렸나

`sajugen/calc/myeongni.py:144-147`

```python
ts = ct.true_solar                       # 진태양시(경도차 + 균시차 보정 완료)
solar = Solar.fromYmdHms(ts.year, ts.month, ts.day, ts.hour, ts.minute, ...)
ec = solar.getLunar().getEightChar()     # ← 4기둥 전부를 이 축에서 뽑는다
```

**진태양시를 시민시각인 것처럼** lunar-python 에 넘긴다. lunar-python 은 내부 절기표(KST 기준)와
이 값을 비교하므로, **월주·연주 절입 판정이 보정량만큼 앞당겨진다.**

절기는 태양 황경이 특정 각도가 되는 **절대 시각**이다. 관측지 경도·균시차와 무관하다.
서울에서 태어나든 뉴욕에서 태어나든 입춘 순간은 같은 물리적 순간이다.
따라서 **절입 판정에 진태양시를 쓰면 안 된다.**

반면 같은 파일 193-201행의 교차검증은 **절대 UTC** 를 쓴다.

```python
utc = ct.utc.replace(tzinfo=None)
sky_branch, _, _ = solarterms.month_pillar_branch(utc)      # 193-194행
ipchun = solarterms.solar_term_time(utc.year, 315)          # 201행
```

**주 산출과 검증이 서로 다른 축**이라 절입 근처에서 반드시 갈린다.

## 3. 결함 창의 폭 — 절대규칙 7의 ±2분으로는 못 덮는다

`eot-window-measure.py` / `eot-window.json` — 1990·2000·2010 × 12절 = **36개 절입 전수**

```
samples                            36
불일치 창이 있는 절입              36 / 36     (전부)
창 폭 평균                         27.72 분
창 폭 최소                         14 분
창 폭 최대                         41 분 이상   (스캔 범위 ±40분에 걸림 = 더 넓을 수 있음)
기존 ±2분 플래그가 전부 덮은 절입   0 / 36
```

> **±2분 은 실측 폭의 1/14 도 안 된다.** 규칙이 가정한 안전 여유가 실제와 한 자릿수 다르다.

창 폭은 그 시기의 `|경도보정 + 균시차|` 와 같다. 서울 기준 대략 **14분 ~ 46분**이며,
균시차가 클수록(2월·11월) 넓다.

## 4. 유파 차이와 결함을 분리해야 한다

같은 "진태양시 적용"이라도 대상에 따라 판정이 다르다.

| 대상 | 진태양시 적용 | 판정 | 근거 |
|---|---|---|---|
| **시지(時支)** | 적용 | **정당 — 우리가 더 정밀** | 시지는 태양의 실제 시각각(hour angle) 문제. 관측지 국지 시각이 맞다 |
| **일주 경계(자시)** | 적용 | **정당 — 유파 차이** | 포스텔러는 경도차만(-32분), 우리는 균시차 포함. 둘 다 '국지 시각' 계열 |
| **월주 절입(節)** | 적용 | **결함** | 절기는 절대 시각. 경도·균시차와 무관해야 한다 |
| **연주 입춘** | 적용 | **결함** | 〃 |

앞선 대조에서 나온 불일치 5건의 재분류:

| ID | 내용 | 재분류 |
|---|---|---|
| A1 | 자시 경계 1분 | 유파 차이 (우리 정당) |
| E1 | 시지 경계 (서울 3/10 09:35) | 유파 차이 (우리 정당) |
| **B2** | 망종 월주 | **우리 결함** |
| **C2** | 입춘 연주·월주 | **우리 결함** |
| F1 | 뉴욕 tz | 우리 결함 (기존 인지, 별도 패킷) |

## 5. 안전망은 작동한다 — 조용히 고객에게 가지는 않는다

`sajugen/pipeline.py:185-187`

```python
if not saju.crosscheck.month_branch_ok:
    reasons.append("월지 lunar↔Skyfield 불일치")
if not saju.crosscheck.year_branch_ok:
    reasons.append("연지 lunar↔Skyfield 불일치(입춘 경계)")
```

→ `order_flow` 가 `CALC_MISMATCH` 로 전이해 **주문을 차단**한다(절대규칙 7).

즉 이 결함은 **틀린 답이 발송되는 형태가 아니라, 정당한 주문이 막히는 형태**로 나타난다.
2026-07-03 감사에서 "문서가 보장하는데 코드가 안 하고 있었다"던 것과 반대로, **여기서는
감지가 제대로 작동하고 있고 주 산출이 틀린 값을 쓰고 있다.**

### 다만 두 가지 잔여 위험

1. **운영자가 CALC_MISMATCH 를 잘못 해소할 수 있다.** 화면에는 "lunar↔Skyfield 불일치"만
   뜨고 *어느 쪽이 맞는지* 안 알려준다. 운영자가 lunar 값(=틀린 값)을 채택하면 오답이 나간다.
2. **빈도**: 12절 × 평균 27.7분 ≈ 연 332분 → 약 **0.063%**. 작지만 0이 아니다.
   월주는 격국·용신·대운의 뿌리라 틀리면 리포트 전체가 무의미해진다.

## 6. 제안 — 규칙을 넓히는 게 아니라 결함을 고친다

### 6-1. 우선순위 1 — 절입 판정 축 분리 (별도 패킷 필요)

`myeongni.build` 에서 **연주·월주는 절대 시각(UTC)** 으로, **일주·시주는 진태양시**로 뽑는다.

- 현재 Skyfield 교차검증이 이미 정답을 계산하고 있다(`month_branch_skyfield`,
  `sky_year_zhi`). **새로 만들 게 아니라 주 산출을 그쪽으로 옮기는 문제다.**
- lunar-python 에 두 번 질의하거나(진태양시용 / UTC용), 월·연주만 Skyfield 판정으로 대체한다.
- **골든 22건 전수 재검증 필수**(절대규칙 20). 경계 밖 케이스는 값이 안 변해야 한다.
- 변경 후 위 36개 절입 창이 **0분**이 되는지 `eot-window-measure.py` 로 재측정한다.

### 6-2. 우선순위 2 — 절대규칙 7의 `±2분` 재정의

현행: "절입 ±2분 이내 출생은 관리자 확인 플래그"

6-1 을 고치면 lunar↔Skyfield 불일치 창은 사라지지만, **경계 자체의 민감도는 남는다.**
±2분의 원래 취지(절기 시각 계산 오차 대비)는 유효하되 근거를 명시해야 한다.

실측 근거:
- Skyfield ↔ KASI 절기 시각 차이는 **669/672 행이 2분 이내, 최대 0.64분**
  (`terms-vs-kasi.json`, 초과 3건은 KASI 자체 결함으로 판정됨)
- 따라서 **계산 오차 대비용으로는 ±2분이 타당하다.** 넓힐 필요가 없다.

> **결론: ±2분을 ±15분으로 넓히자는 내 앞선 제안은 철회한다.**
> ±15분이 필요해 보였던 이유는 6-1 결함 때문이었고, 결함을 고치면 근거가 사라진다.
> 규칙을 실측 없이 느슨하게 바꿨다면 **결함을 정책으로 덮는** 최악의 수가 됐을 것이다.

### 6-3. 우선순위 3 — CALC_MISMATCH 화면에 판정 근거 추가

운영자가 어느 쪽이 맞는지 알 수 있어야 한다. 현재 경고문은 두 값만 보여준다.

```
현재: "월지 lunar(丑)↔Skyfield(寅) 불일치"
제안: "월지 lunar(丑)↔Skyfield(寅) 불일치 — 절입 2000-02-04 21:40 KST(KASI),
       출생 절대시각 21:27 → 절입 이전 → Skyfield(丑) 채택 권장"
```

### 6-4. 우선순위 4 — 시지·자시는 손대지 않는다

유파 차이이고 우리 쪽이 정당하다. 다만 **고객 응대 문구**는 필요하다.

> 타 서비스와 시(時) 기둥이 다르게 나올 수 있습니다. 저희는 출생지의 실제 태양 위치
> (균시차 포함)로 시각을 계산하고, 일부 서비스는 경도차만 반영합니다. 계산 방식의 차이이며
> 어느 한쪽이 틀린 것이 아닙니다.

(절대규칙 11 — 정확도 우위 주장으로 읽히지 않게 "차이"로만 서술)
