## 2. 코딩 작업 표준 사이클 — 요청 한 건의 생애

### 2-1. 시작 전: 2문장을 먼저 쓴다 (30초)
어떤 요청이든 에이전트에게 말하기 전에 메모장에 이 2문장을 완성한다:
1. **무엇을**: "___ 가 ___ 하게 만들고 싶다" (한 문장, 구체적으로)
2. **완료 기준**: "___ 를 실행했을 때 ___ 가 나오면 완료다" (검증 가능하게)

2번을 못 쓰겠으면 아직 요청할 준비가 안 된 것이다 — 그때는 "구현해줘"가 아니라
"조사해줘/선택지 줘"로 시작한다. 근거: 에이전트에게 pass/fail 신호를 주면 스스로 검증 루프를
닫는다 (https://code.claude.com/docs/en/best-practices).

### 2-2. 계획: 플랜모드로 받고, 승인 전에 4가지를 본다
큰 작업(파일 여러 개, 계산/게이트/주문 경로)은 반드시 플랜모드로 계획부터 받는다.
diff 를 한 문장으로 설명할 수 있는 작은 작업(오타, 문구 1줄)은 계획 생략 — 매번 계획을 시키면
흐름만 느려진다 (같은 출처).

계획서에서 **승인 전 확인 4가지**:
1. 수정 파일 목록이 있는가 — 내가 아는 파일인가, 왜 이 파일들인가
2. 검증 방법이 있는가 — "테스트 추가"가 아니라 "어떤 입력이 어떻게 실패/통과하는지"
3. 리스크/회귀 우려가 적혀 있는가 — 없다고 쓰여 있으면 오히려 의심
4. 기존 게이트/차단 코드에 손대는가 — 손댄다면 "완화 아님"의 근거가 있는가

하나라도 비면 승인하지 말고 그 항목을 되묻는다.

### 2-3. 큰 작업은 쪼갠다: 한 세션 = 한 단위, 인계는 지시문 파일로
- 큰 작업은 Phase 로 쪼개고 **한 세션이 한 Phase 만** 한다. 컨텍스트가 길어진 세션은 판단력이
  떨어진다. 실증: 감사 후속 로드맵(Phase 1~5)을 세션 분할로 완주, 오류 0.
- 세션을 넘길 때는 대화 요약이 아니라 **self-contained 지시문 파일**을 만들게 한다. 견본:
  `handoff/audit-followup-roadmap.md`. 필수 구성: (0) 세션 프로토콜 (0-1) 불변 가드
  (0-2) **내가 이미 결정한 것(재질문 금지)** + Phase/태스크별 [파일:라인 + 수정 지시 + 검증 방법].
- 기결정을 안 적으면 받는 세션이 나에게 같은 질문을 다시 한다 — 내 시간이 새는 지점.

### 2-4. 완료 판정: 증거 3종 없으면 미완료
에이전트의 "완료했습니다/해결됐습니다"는 **판정이 아니라 주장**이다. 다음 3종을 확인하기 전까지
미완료로 취급한다:
1. 실행한 검증 명령 (예: `./.venv/Scripts/python.exe -m pytest tests/ -q`)
2. 그 출력 (passed 수 / exit code — "513 passed / 4 skipped / exit 0")
3. 커밋 SHA

없으면 이 한 줄만 보낸다: **"증거 보여줘 — 명령, 출력, SHA."**
근거: Anthropic 공식 실패 패턴 "trust-then-verify gap"(그럴듯하지만 엣지케이스가 틀린 구현) —
항상 검증을 제공하게 하고, 검증 못 하면 배포 금지 (https://code.claude.com/docs/en/best-practices).
실증: "고쳤다는데 반복된다" 사고의 뿌리가 정확히 이 갭이었고, 전수 감사에서 문서-코드 불일치
6건(자시 정책 무효 P0 포함)이 테스트 GREEN 상태로 숨어 있었다.

### 2-5. 검수: 비전공자인 내가 diff 에서 볼 수 있는 것
코드를 다 이해하지 못해도 다음은 볼 수 있고, 이것만으로 사고 대부분을 거른다:
1. **테스트가 같이 늘었나** — 코드만 바뀌고 tests/ 가 안 바뀐 계산/게이트 수정은 반려
2. **빨간 줄(삭제)에 게이트/차단/lint 코드가 있나** — 있으면 "이거 완화 아니야?"라고 질문
3. **커밋 메시지에 측정치가 있나** — "개선했다"가 아니라 "20/42mm -> 31/31mm" 같은 숫자
4. 고위험 변경(계산·게이트·주문·결제·PII)은 **만든 에이전트가 아닌 별도 세션**(Codex Verifier
   또는 새 Claude)에 diff 만 주고 검토시킨다. 근거: fresh-context 적대 리뷰(위 Anthropic 문서).

### 2-6. 주기 루틴 (달력에 박아두기)
| 주기 | 할 일 | 명령/방법 |
|---|---|---|
| 주 1회 | 백업 + E2E | docs/18 §8 백업 명령 / `SAJUGEN_RUN_E2E=1` pytest |
| 월 1회 | 전수 감사 세션 | tmp/audit_brief.md 방식 — 플랜모드로 "회의적 재검증" 지시. 실증: P0 2건 적발 |
| 분기 1회 | 백업 복원 테스트 + 키 로테이션 | 백업 파일 열어 count 확인 / .env 키 갱신 |

## 3. 에이전트에게 말하는 법

### 3-1. 황금률
"**맥락을 모르는 동료에게 이 요청을 그대로 보여줬을 때 헷갈리면, 에이전트도 헷갈린다.**"
(https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### 3-2. 좋은 지시의 3요소 + 내 실제 사례
구체 증상/목표 + 검증 가능한 완료 기준 + 맥락·기결정.
- 좋았던 실례: "PDF 레이아웃이 다 틀어져 있고, 이 오류가 수십 번 반복된다" — 증상 + 빈도 덕에
  에이전트가 "반복 = 감지 시스템의 구멍"이라는 근본원인 층까지 팠다.
- 나쁜 형태: "알아서 좋게 고쳐줘" — 무엇이 좋음인지 에이전트가 추측하게 만든다. 추측은 곧
  "그럴듯하지만 내 의도와 다른 결과"다.
- 프롬프트 구체화 4패턴(Anthropic 공식): (1) 범위 지정("이 파일/이 시나리오만"),
  (2) 답이 있는 소스 지목("공식 문서/이 파일을 봐라"), (3) 기존 패턴 예시("gunghap.py 방식처럼"),
  (4) 버그는 증상 + 추정 위치 + "고쳐진 상태" 서술.

### 3-3. 모르겠으면 인터뷰를 시켜라
큰 기능인데 요구사항이 흐릿하면, 내가 스펙을 쓰지 말고 이렇게 시작한다:
"이 기능을 만들기 전에, 네가 나를 인터뷰해서 요구사항을 뽑아내고 SPEC 문서로 저장해줘.
기술 선택, 화면, 엣지케이스, 범위 밖까지 질문해라." -> 나온 SPEC 을 검토·승인 -> 새 세션에서
그 SPEC 으로 구현 (https://code.claude.com/docs/en/best-practices 의 공식 패턴).

### 3-4. 요구 습관 5가지 (매 세션 반복해도 됨)
1. "완료라고 하기 전에 **증거**(명령+출력+SHA) 먼저."
2. "확인 못 한 것은 **미검증**으로 분리해서 보고해."
3. "게이트/차단 코드에 손댔으면 **완화가 아닌 근거**와 양방(통과/차단) 테스트를 보여줘."
4. "조사 결과에는 **출처 URL** 필수. 접근 실패면 실패라고 써."
5. "확실하지 않으면 **모른다고 말해라**. 아마/~일 것 금지."

## 4. 자료조사 방법론 — 오류 없는 조사

### 4-1. 기술 자료 신뢰 서열 (실무 관행 — 원리는 "출처 뒤의 책임 구조")
위에서 아래로 내려갈수록 검증 책임이 사라진다. **결정은 항상 위 2단계 안에서 근거를 확보**한다:
1. **공식 문서** — 사용법·보장 범위의 최종 권위
2. **릴리스 노트/체인지로그** — "언제 무엇이 바뀌고 고쳐졌나". 실증: iztro-py 0.3.5 릴리스노트
   한 줄이 대한(大限) 배정 버그 잔존을 확정해 줬다
3. **이슈 트래커(GitHub Issues)** — 알려진 버그·한계. 실증: lunar-python #32 가 자시 일주 문제의
   실증 근거였다
4. 벤더/개발자 블로그 — 배경과 의도(사실 확인은 위에서)
5. 커뮤니티(스택오버플로 등) — 힌트로만, 반드시 위로 역추적
6. **AI 답변 — 시작점일 뿐, 절대 종착점 아님.** 근거: LLM 생성 코드 57.6만 샘플에서 의존성의
   19.7%가 존재하지 않는(환각) 패키지였다 (https://arxiv.org/html/2502.18468v1). AI 가 알려준
   API/옵션/패키지는 공식 문서에서 존재부터 확인한다.

### 4-2. SIFT 4단계 — 기술 조사 실전 절차 (원저자 https://hapgood.us/2019/06/19/sift-the-four-moves/)
1. **Stop**: 그럴듯한 답을 찾자마자 적용하고 싶은 충동을 멈춘다. "이 출처가 뭔지 아는가?"
2. **Investigate the source**: 읽기 전에 출처부터 — 공식인가, 개인 블로그인가, 몇 년도 글인가,
   내 버전에 해당하는가.
3. **Find better coverage**: 그 글에 매달리지 말고 같은 주제의 더 나은 출처(공식 문서·복수 출처)를
   새로 찾는다. 전문 팩트체커가 일반인과 다른 점이 바로 이 "수평 읽기"다 — 페이지 안에 머물지
   않고 새 탭에서 교차 검증 (Stanford SHEG 연구,
   https://ed.stanford.edu/news/it-doesn-t-take-long-learn-how-spot-misinformation-online-stanford-study-finds).
4. **Trace claims**: 주장·수치·코드 조각을 원출처 맥락까지 추적한다. 블로그가 인용한 공식 문서를
   직접 열어 그 말이 정말 있는지, 조건이 붙어 있는지 확인.

### 4-3. 문서를 고르는 법 — Diátaxis 4유형 (https://diataxis.fr/)
읽기 전에 "나는 지금 무엇을 하려는가"를 정하고 맞는 유형으로 간다:
- **배우려면** 튜토리얼 / **지금 작업을 끝내려면** 하우투 가이드 /
- **정확한 사실·API 를 확인하려면** 레퍼런스 / **왜 이렇게 설계됐는지 이해하려면** 설명(explanation)
- 흔한 실수: 급한데 튜토리얼을 처음부터 따라가기, 개념이 궁금한데 레퍼런스만 뒤지기.

### 4-4. 라이브러리 도입/업그레이드 전 체크 5줄
1. 최신 버전·릴리스 날짜(버려진 프로젝트인가?) 2. 내 버전과 최신 사이의 체인지로그(breaking?)
3. 이슈 트래커에서 내 사용처 관련 open 이슈 4. 라이선스(상용/서비스 노출 가능?)
5. **적용 후 골든/전수 테스트 재검증** — 계산 스택은 예외 없음(절대규칙 2).

### 4-5. AI 에게 조사를 시키는 법 (내 표준 지시문 — 복붙용)
```
[주제]를 조사해줘. 규칙:
- 실제 WebSearch/WebFetch 로 확인하고, 모든 주장에 출처 URL 을 붙여라.
- 공식 문서/릴리스노트/이슈 트래커를 우선하고, 블로그·커뮤니티는 원출처로 역추적해라.
- 접근 실패한 자료는 "조사 실패"로 명시해라. 추측으로 메꾸지 마라.
- 내 코드/버전과 대조해서 "어긋남/리스크/영향 없음"으로 분류해라.
- 확실하지 않은 것은 "미확정"으로 분리해라.
```
실증: 이 형식의 조사가 전수 감사에서 iztro 버그·모델/SDK 정합·Starlette 크래시 조합을 전부
1차 자료로 확정했다.

## 5. 오류가 났을 때 — 디버깅 프로토콜

1. **같은 명령을 다시 돌리지 않는다.** 두 번 같은 오류면 원인 조사로 전환 (docs/17, 실증:
   QI-2026-06-24-07 — 반복 시도로 시간만 태운 사고).
2. **에러 원문을 그대로** 조사한다(요약·의역 금지). 에러 메시지가 가장 정확한 검색어다.
3. 재현을 최소화한다 — "어떤 최소 입력에서 터지는가"를 좁히면 원인의 절반을 찾은 것.
4. 1차 자료(공식 문서·이슈)에서 알려진 문제인지 확인 후, 가설은 **한 번에 하나씩** 검증.
5. 고치기 전에 **그 버그를 재현하는 테스트부터** 만들게 한다(회귀 우선, docs/18 §3).
6. 고친 뒤에는 "왜 지금까지 못 잡았나"를 묻는다 — 감지 구멍을 같이 메워야 재발이 끝난다
   (10-methodology A-6). 사고면 docs/16 에 기록.

## 7. 빠른 참조 카드

**세션 시작 템플릿(복붙):**
```
[프로젝트]에서 [무엇을 한 문장]. 완료 기준: [명령]을 실행하면 [기대 출력].
이미 결정된 것: [기결정 — 재질문 금지]. 제약: [건드리면 안 되는 것].
큰 작업이면 플랜모드로 계획부터. 완료 보고는 증거(명령+출력+SHA) 포함.
```

**완료 확인 3줄 체크:**
1. 검증 명령과 출력(passed/exit 0)을 봤는가?
2. 미검증 항목이 분리 보고됐는가?
3. 게이트/차단 코드 삭제가 diff 에 없는가(있다면 근거 확인)?

**자주 쓰는 명령(sajugen):**
- 전체 테스트: `./.venv/Scripts/python.exe -m pytest tests/ -q`
- 하네스 검증: `./.venv/Scripts/python.exe scripts/hrun.py --profile harness/profiles/local/personal_h153.yml`
- 백업: docs/18 §8 / 주문 삭제(파기): `python -m sajugen.delete_order <id> --yes`

**배움의 원칙:** 튜토리얼을 따라만 하지 말고, 항상 내 프로젝트에 **튜토리얼과 다른 것 하나**를
직접 추가해 본다 — 그 지점에서 진짜 배움(능동 조사)이 시작된다
(https://blog.boot.dev/education/building-your-first-coding-project/). 나의 경우: 에이전트가 만든
코드에서 매주 한 파일을 골라 "이 파일이 뭘 하는지 설명해줘, 내가 질문할게" 세션을 갖는 것이
같은 효과다.
